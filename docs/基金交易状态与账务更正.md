# 基金交易状态与账务更正

## 这轮解决什么

以前录入买卖就直接改变持仓，删错一笔交易也会直接抹掉原记录。
现在把“正在办理的外部申请”和“已经确认的成交”分开，并保留更正前后的记录。

**这仍是个人记账系统，不会向银行、支付宝或基金公司下单、撤单，也不会转账。**
Agent 继续读取持仓进行分析，不拥有这些交易写入工具。

## 网页怎么用

入口：我的资产 → 持仓 → **记账与流水**，对应 `/#assets/transactions`。

### 已经成交，只想补记一笔

选择“已成交”，选择基金和买入/卖出，按平台确认单填写成交净值日、份额、净值和手续费。
保存后重算持仓、剩余成本和已实现盈亏。净值输入不再自动填写最新行情，避免把今日净值误当成历史成交净值。
基金选项来自已关注基金与当前持仓的并集；新基金先在侧栏搜索并加入基金库。

### 外部平台刚提交，还没确认

选择“待确认”：买入填写含费申购金额，卖出填写申请份额，申请时间统一按北京时间。
保存后，在右侧“交易申请”的“登记结果”菜单继续处理。

| 操作 | 账本发生什么 |
| --- | --- |
| 登记买入申请 | 增加待确认金额，不增加基金份额 |
| 登记卖出申请 | 占用可用份额，不提前减少持有份额或确认盈亏 |
| 登记成交确认 | 按实际确认单生成一次成交流水，更新持仓和成本 |
| 登记撤单申请 | 状态为撤单处理中，卖出占用仍然保留 |
| 登记撤单成功 | 根据实际结果结束申请，解除占用，不生成成交 |
| 登记撤单失败 | 回到待确认，仍可登记后续成交 |
| 登记申请失败 | 结束申请并解除占用 |
| 登记赎回到账 | 仅在卖出已确认后登记实际到账日，从待到账金额中移除 |

每个处理动作都要填写外部结果依据。撤单是否允许、何时成功和退款何时到账，以外部平台及产品规则为准。
系统不会到 15:00 自动撤单，也不会到了预计确认日就擅自增加持仓。
买入撤单成功不代表退款已经到账；本版未建立退款账户。

### 之前记错了

在“成交流水”的“更正流水”菜单中选择：

- **更正记录**：填写正确内容和原因，原记录标为已更正，另外追加一笔有效记录。
- **冲正误录**：整笔记录不应存在时使用，必须填原因，原记录保留但退出当前成本计算。

这里的“冲正”是本地误录的纠正，不是取消外部真实成交，也不是卖出基金。
持仓已经买入、现在想减仓，应该登记新的卖出，不能冲正原来的买入。
如果更正导致后续历史卖出超过当时份额，或影响其他未决赎回的占用，整个操作会回滚。
已有历史的账本不能整体覆盖或删除，原来的 DELETE 流水接口会明确提示使用更正。

## 可以这样验收

新建独立测试组合，初始录入某只已关注基金 **1000 份、成本 1000 元**。不要拿真实账本填测试数据。
所有申请和成交日期均填写已经过去的日期，成交净值日不得早于申请日，确认日不得早于净值日。

1. 登记卖出申请 300 份。仍持有 1000 份，占用 300 份，可用 700 份。
2. 登记撤单申请。占用仍为 300 份。
3. 登记撤单成功。可用恢复到 1000 份，成交流水没有新增卖出。
4. 重新登记卖出 300 份，再登记确认：净值 1.20、手续费 0.50。持仓变为 700 份，净收入 359.50 元，本笔已实现盈亏 59.50 元。
5. 此时“赎回待到账”为 359.50 元。登记实际到账日期后归零，不重复减少持仓。
6. 更正该卖出的手续费为 0.10 元。原流水仍可查，新流水净额 359.90 元，已实现盈亏变成 59.90 元。
7. 尝试再申请卖出 800 份，应提示份额不足；页面保留输入，数据库不产生申请。

网络超时后在当前页面原样重试，会复用请求键；修改内容会产生新键。
刷新整个浏览器或重新打开页面后，应先核对历史是否已保存，不要直接重录。

## 代码如何组织

| 文件 | 职责 |
| --- | --- |
| `app/services/portfolio_trade_contracts.py` | 校验申请、结果登记、更正请求，禁止字段混用 |
| `app/services/portfolio_trades.py` | 状态流转、幂等检查、确认生成流水、更正链与事件 |
| `app/services/portfolio_ledger_values.py` | Decimal 数值边界、金额舍入、精确值读写 |
| `app/services/portfolios.py` | 有效流水重放，移动平均成本，持有/占用/可用份额 |
| `app/services/portfolio_performance.py` | 收益曲线排除已冲正原记录，沿用正确的业务顺序 |
| `app/models.py` | 交易申请、处理事件、更正记录，以及旧流水的精确值列 |
| `app/routers/portfolios.py` | 当前用户隔离和 HTTP 错误映射 |
| `app/static/portfolio-bookkeeping.js` | 独立记账工作区、草稿、重试键、状态菜单 |
| `app/static/portfolio-bookkeeping.css` | 沿用现有深色工作台的表单与流水样式 |

数据流：**网页登记 → FastAPI 校验身份和输入 → 锁定组合 → 校验状态与幂等键 → 写事件/流水 → 重放持仓 → 同一事务提交 → 网页重读。**
PostgreSQL 使用组合行锁；SQLite 在读取和检查前开启 `BEGIN IMMEDIATE` 写事务。
唯一索引为同一用户、组合及请求键提供第二道约束。并发申请不能各自看见同一份可用余额后重复占用。

## 精度与迁移

新输入：金额和费用保留 2 位、份额 4 位、净值 6 位，采用 Decimal 与 ROUND_HALF_UP。
部分卖出按分释放成本，最后清仓释放全部剩余成本，避免留下一分钱尾差。
更正另记实际写入时间，同时继承原记录的业务排序键，避免同日先买后卖顺序被改乱。

为兼容现有 SQLite/PostgreSQL 数据，这轮没有直接改旧 FLOAT 列的类型。
新流水在 `exact_values` JSON 中保存权威的十进制字符串，旧数值列继续作为兼容投影。
旧记录不补造已经丢失的精度；若没有精确值列内容，按原存储数值读取，不强行截断旧净值。
**这不等于完成 PostgreSQL NUMERIC 全表迁移。图表和行情计算仍可能使用浮点展示值。**

Alembic revision：`aa19c8e7b602`，从 `92b7d631ea04` 追加三张表和 `exact_values` 列。
正式迁移流程应先备份数据库、停止写入，再运行 `python -m alembic upgrade head`，最后启动服务。
本地项目另有 `create_schema` 的兼容补列机制；如果先启动新代码自动建了表，不要盲目重跑相同 DDL，应核对实际表结构和 Alembic 版本。

## 当前边界

- 已实现完整的本地申请、确认、撤单结果、赎回到账登记和误录更正；不是基金销售系统。
- 不自动接收外部回单，不自动核对银行余额，不提供资金可用余额或实际支付能力。
- 当前只支持整笔确认，不自动处理部分成交、部分赎回确认、分批到账、退款和复杂份额冻结。
- 确认与关联更正必须符合申请金额/份额；申请本身录错时，需要冲正错误确认并重新登记，不能冒充部分确认。
- 还不是银行复式总账，未实现借贷分录平衡、日终对账、复核审批和数据库级防篡改。
- 前端本轮接入 Web；小程序尚未增加新流程，旧删除操作会被服务端拒绝。
