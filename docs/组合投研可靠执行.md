# 组合投研可靠执行

更新时间：2026-09-16。

## 解决什么问题

以前 SQL 里保存 Job 后，API 还要单独把消息发到 Redis。如果中间断电，任务可能一直
排队却没有消息；Worker 运行中退出，旧的 `running` 状态也不会自己恢复。

现在把“任务记录”和“待投递清单”一起存入数据库。有人负责持续检查这张清单，发送
失败就稍后再发。Worker 领取后定期续约，只有租约真的过期，其他 Worker 才能接管。

本轮仅覆盖新建的 `portfolio_research` 组合投研 Job。普通聊天、组合调整审批、采集、
交易记录、文件工具等仍使用原有机制；没有批量重跑历史任务，也没有新增自动行情刷新。

## 数据流

```text
组合页 / AI 对话发起研究
  -> 同一 SQL 事务：background_jobs + reliable_job_states + job_outbox
  -> API 中的投递循环：领取一条 Outbox，事务外发送消息
  -> Local 线程 / Celery Worker：校验事件版本，领取执行租约
  -> 独立心跳线程续约，原 JobRunner 执行 LangGraph
  -> 冻结输入快照 -> 并行研究 -> 模型解释 -> 汇总报告
  -> 带 owner_token + execution_version 校验写入唯一有效结果
  -> 原有 SSE / 小程序轮询展示进度和报告
```

队列发出消息不代表 Worker 已经收到。`sent` 超过领取等待时间仍未被消费，也会补投。
补投是“至少一次投递”，不是“只发送一次”；同一事件只有一个 Worker 能领取成功。

## 故障时怎么处理

| 故障 | 处理 |
| --- | --- |
| API 在 SQL 提交后退出 | 重启后扫描到 Outbox，继续投递同一个 Job |
| Redis 暂时不可用 | Job 保持排队，页面提示已保存、等待自动补投 |
| 消息重复到达 | 校验事件版本和当前状态，重复消息直接跳过 |
| 模型很慢，但 Worker 仍正常 | 独立心跳维持租约，不因无输出就抢任务 |
| Worker 被强制结束 | 租约到期后回队，接管次数有限 |
| 旧 Worker 稍后恢复 | 旧版本不能写进度/结果，也不能污染新分区的 checkpoint |
| 图已完成，Job 尚未写完成 | 接管后直接从 checkpoint 取报告，不再次调用模型 |
| 用户取消 | 取消状态优先，后续心跳/工具调用边界和结果写回被拒绝 |
| 额度不足 | 停止自动重试，不通过换 Worker 获得新预算 |

`Job ID`、冻结 `snapshot_id`、模型预算的 `run_id` 始终不变。每次领取生成新的内部
checkpoint thread，复制上一轮最近的完整状态和 pending writes，再恢复尚未完成步骤。
旧 Worker 即使还在写 checkpoint，也只能写旧分区。

## 使用方式

照常在组合研究入口点击分析即可，Web 和小程序共用这一套后端，不需要新开页面。
现有任务进度会显示排队、投递失败、接管、断点恢复、完成等信息。
任务接口新增 `recovery` 摘要：执行版本、恢复次数、异常重试次数、心跳和总截止时间。
报告的 `graph_trace.checkpoint_thread_id` 可定位最终断点；不会公开执行权 Token。
`GET /background-jobs/runtime` 中的 `reliable_research.delivery_loop_running`
可检查当前 API 进程是否已经启动投递循环。

本地开发自动创建两张新表。生产环境先迁移数据库，再同时更新 API 和 Worker：

```bash
conda activate dl
python -m alembic upgrade head
```

不要在旧 API/Worker 仍消费队列时混用新版本。不同执行版本需要理解同一套租约协议。
所有进程必须使用相同的业务库、持久化 checkpoint 库和 `JOB_EXECUTION_MODE`。

## 配置与边界

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `RELIABLE_RESEARCH_JOBS_ENABLED` | `true` | 新任务是否纳管；关闭后旧纳管任务仍受保护 |
| `JOB_LEASE_SECONDS` | `60` | 执行租约；心跳每 20 秒续约 |
| `JOB_RECOVERY_MAX_ATTEMPTS` | `2` | 失联最多接管两次，与普通异常重试分开计数 |
| `JOB_OUTBOX_POLL_SECONDS` | `2` | 待投递与过期租约扫描间隔 |
| `JOB_DELIVERY_ACK_SECONDS` | `30` | 已发送但未领取时，多久补投 |

任务总执行期限从第一次领取开始计算，包含重试、恢复和中间等待；接管不重置超时。
SQL 租约采用数据库时间。心跳续约不能证明第三方请求已停止，只能证明执行权仍有效。

API 至少需要一个副本在线运行投递循环。本地 `local` 模式下，API 关闭后没有独立
Worker；再次启动 API 才会恢复。Celery 模式下还需要独立 Worker 在线消费队列。

本轮不承诺供应商调用或计费恰好一次。如果请求已到达模型服务，但响应/usage 未保存
时 Worker 退出，恢复可能重新调用该步骤。此前消耗保留为预留或待确认，仍占原任务
额度，不能按零费用处理。最终只允许当前执行版本提交一份权威报告。

当前断点迁移仅适用于本研究图的单 namespace、完整状态 channel；以后引入子图或
DeltaChannel，必须扩展迁移协议。`memory` checkpoint 不支持该持久恢复功能。
历史 checkpoint 和 Outbox 暂保留用于排障，尚未增加自动归档清理。

## 代码导读

| 文件 | 职责 |
| --- | --- |
| `app/services/job_store.py` | 保存 Job 时同事务登记投递记录 |
| `app/services/reliable_jobs.py` | SQL 状态转换、租约、版本校验、补投与接管规则 |
| `app/services/job_delivery.py` | 有界扫描与事务外投递，不执行研究或采集 |
| `app/services/reliable_job_runtime.py` | 心跳线程、带租约 Store、复用原任务预算 |
| `app/services/job_runtime.py` | 原研究业务调度和进度回调 |
| `app/services/portfolio_research_graph.py` | 独立 checkpoint 分区、迁移与恢复 |
| `app/worker_tasks.py` | Celery 分流入口，不凭 redelivered 标志擅自接管 |

## 自动化验证

以下测试只使用临时数据库、固定业务数据和假模型，不调用收费 API：

```bash
conda activate dl
python -m unittest tests.test_reliable_jobs tests.test_reliable_research_checkpoints tests.test_reliable_job_process -v
```

真实 PostgreSQL / Redis 集成测试为可选项，连接自己的专用测试实例后运行：

```bash
# 设置 TEST_RELIABILITY_POSTGRES_URL，测试创建并删除随机 schema。
python -m unittest tests.test_reliable_jobs_postgres -v
# 设置 TEST_JOB_REDIS_URL，测试只清理自己的随机 key 前缀。
python -m unittest tests.test_reliable_job_celery -v
```

进程测试会在模型步骤中、以及图已完成但尚未提交 Job 时分别强制结束子进程，再新建
进程恢复。它验证的是真实持久化断点与进程丢失，不是只把数据库状态手动改成失败。
