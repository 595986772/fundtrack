# 基金交易与收益时间

## 页面怎么用

小程序「资产 → 交易记账」选择基金与买卖方向，在「收益时间」里选择交易渠道、下单日期和北京时间，点击「计算收益日期」。预览不会下单或修改持仓，也不调用大模型。

普通国内场外净值型基金会得到三个日期：

| 日期 | 含义 |
| --- | --- |
| 预计成交净值日 T | 以哪一天的收盘净值成交，不是提交申请时看到的最新净值 |
| 预计份额确认日 | 通常为下一交易日 T+1；销售平台何时显示确认结果可能更晚 |
| 首个收益净值日 / 最后收益净值日 | 买入后首个后续交易日的净值变化 / 卖出份额最后承担涨跌的净值日 |

例如普通场外基金，2026-09-11（周五）14:00 买入，预计使用周五净值，首个收益净值日为 09-14（周一）；16:00 买入，预计使用周一净值，首个收益净值日为 09-15（周二）。2026-09-30 15:01 提交则跨国庆假期，预计净值日为 10-08、确认日与首个后续收益净值日为 10-09。

“有收益”在这里指开始计入净值涨跌，可能亏损或不变，不是保证赚钱。手续费也会影响盈亏。净值披露和平台确认完成后，结果才可能展示；不保证某个具体钟点。债券基金等的假期收益可能合并到后续净值中。

## 记账与下单分开

- 页面下方仍只记录已经确认的真实成交，填写回单上的成交净值日、份额、净值和手续费。
- 原「成交确认日」改名为「成交净值日」，因为账本按净值日计算，不能把 T+1 确认日误填成 T 日。
- 「按此净值日填写」需要显式点击，不能应用未来日期，不会自动填写成交价格或份额。
- 实际回单与通用估算不同时，保存两种日期并提示差异；账本采用实际填写的回单日期，不悄悄重写事实。
- 保存时后端自行重新估算；不接受前端传入的任意时间结论。原始下单时间、规则版本、估算日期和来源保存在流水 `timing` JSON 中。
- 旧流水没有原始下单时间，保持 `timing = null`。记账创建时间不能冒充下单时间。
- 不新增待成交订单、自动确认任务或自动行情刷新。真实平台还未确认时，只预览，不提前记入持仓。

## 规则与边界

1. 时区固定 Asia/Shanghai。交易日 15:00 前按当日净值，15:00 及之后按下一交易日估算；恰好 15:00 的受理边界以渠道回执为准。
2. 使用项目已有 `exchange_calendars` 的 XSHG 交易日历，不是简单排除周末。节假日、周末调休均按休市处理。
3. 本机依赖当前覆盖至 2026-12-31；完整计算需要的下一交易日超出覆盖范围时返回 `calendar_unavailable`，不编造工作日。后续年度需要更新日历依赖。
4. QDII、FOF、货币基金、境外/港股类、持有期/定开/封闭产品、非联接 ETF 和未知类型返回 `manual_required`。逐产品开放日、暂停申赎及新发认购规则尚未接入，普通基金估算也以正常开放为前提。
5. 场内成交不套用场外 15:00 规则；赎回确认日也不是资金到账日。

## 模块与接口

- `app/services/fund_transaction_timing.py`：可独立测试的时间轴计算，读取本地基金档案及日历。
- `POST /api/v1/funds/{fund_code}/transaction-timing`：只读估算接口，允许预览计划时间。
- `app/services/portfolios.py`：确认交易保存时间快照，仍用成交净值日重放流水；幂等性比较原始输入，不受后续日历版本变化影响。
- `app/models.py` / Alembic `31ab8d4f9c02`：流水只追加 nullable JSON 列，本地兼容迁移不改旧值。
- `miniprogram/src/lib/trade-timing.ts`：组装显式 `+08:00` 时间，不在客户端重写交易日算法。
- `miniprogram/src/pages/transactions/`：输入、预览、显式应用日期与历史快照展示；切换基金/方向/时间或离开页面后丢弃旧响应。
- `miniprogram/preview/runtime.js`：原生日期和时间 picker 的浏览器适配。

请求示例：

```json
{
  "submitted_at": "2026-09-30T15:01:00+08:00",
  "transaction_type": "buy",
  "channel": "off_exchange"
}
```
