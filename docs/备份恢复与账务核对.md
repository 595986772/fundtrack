# 备份恢复与账务核对

## 这次解决什么问题

第一步的调用链回答“任务为什么慢、卡在哪里”；这一步回答“服务器的数据丢失后，
能不能找回来，找回来以后账是不是对的，会不会把旧任务又执行一次”。

当前实现是**单机 PostgreSQL 16 正式 Compose 的维护窗口逻辑备份与隔离恢复演练**。
不是点击一下就覆盖线上数据库，也不是 PostgreSQL 时间点恢复（PITR）。
本机 SQLite 开发模式不在本脚本的备份范围内。

```text
显式同意暂停写入
  → 暂停入口、API、Worker、OpenFGA
  → 业务库 + 授权库 + 原始资料 + 核对基线
  → 校验停写期间数据库未变化 → 发布完整备份 → 恢复原本运行的服务
  → 在新建的隔离环境中恢复
  → 核对数据库内容、文件和账本
  → 隔离旧任务/授权/定时策略 → 输出报告 → 默认清理演练环境
```

**当前没有连接你的云服务器，也没有配置异地存储或定时备份。**
脚本需要在能访问目标 Docker 的服务器上运行；备份目标可以是已经挂载好的独立备份盘。
同一服务器磁盘上的另一文件夹，只是副本，不算异地容灾。

## 备份范围

| 内容 | 处理方式 |
| --- | --- |
| 业务 PostgreSQL | `pg_dump -Fc`，包括交易、持仓、任务、报告、调用用量、同库 Checkpoint |
| OpenFGA PostgreSQL | 单独的完整数据库逻辑备份，包括授权模型、关系和存储信息 |
| 资料卷 | 保存 `docs`、`fund_reports`、`chroma`、`memory`、`tasks`、`schedules`、`agent_notes`、`agent_context`、`social_media`、`openfga.json` |
| 核对基线 | 每张用户表的行数/内容 SHA-256、序列状态、账本重放结果、未完成任务及待确认用量数量 |
| 完整性清单 | 每个备份文件和资料文件的长度、SHA-256、资料卷根目录属主/权限、备份时间、源镜像 ID |
| 不备份 | Redis 队列、浏览器登录 Profile、运行日志/Trace、`.env`、TLS 证书、部署密钥、Git Worktree |

这里的数据库备份不包含集群全局角色/口令/ACL；隔离环境由 Compose 创建自己的角色，
恢复使用 `--no-owner --no-acl`。自定义扩展、表空间、独立 Checkpoint 数据库不属于当前支持布局。
部署配置、镜像和密钥应另行保管，不能只留一份数据包就认为整台服务器都能重建。

备份包**未加密**，数据库中包含用户资料、账务、登录口令哈希等敏感内容。
目录权限为 `700`，文件为 `600`，但这不能替代加密。正式使用应存到受限、加密的独立存储，
传输使用 SSH/TLS，不要放进 Git、静态网页目录或公开对象存储。
SHA-256 用来发现损坏，不是来源认证；只能恢复自己可信的备份。

## 部署前检查

需要 Docker Compose v2、Python 3.11+ 和本仓库代码。在**与备份对应的代码版本**下执行；
恢复报告会记录源镜像 ID，但不会自动下载源镜像或适配任意历史 Schema。

1. 正式服务已完成数据库迁移，源项目名与配置文件准确。
2. 一个 API 和一个 Worker 共用 `/app/data` 命名卷，两套数据库均已运行。
3. `CHROMA_PERSIST_DIR=/app/data/chroma`，`FUND_REPORT_STORAGE_DIR=/app/data/fund_reports`。
4. Checkpoint 使用业务 PostgreSQL；其他自定义资料目录需要先纳入明确的备份范围。
5. 不要同时运行迁移、外部写入程序或第二份备份。脚本有同一检出目录的维护锁，
   不是跨主机分布式锁；维护期间的两次数据库指纹比较也不能替代停写要求。
6. 选择业务空闲时间。`--stop-writers` 会导致短暂不可用，每个服务最多等待 60 秒退出。
   未完成模型请求仍可能在供应商侧计费，未知用量需要事后核对。

### 旧季报目录需要注意

本次正式配置把季报和向量目录固定到了共享卷。旧版本的相对路径可能实际落在
容器的 `/app/app/data/fund_reports`、`/app/app/data/chroma`，而不是 `/app/data`。

**已有部署不要先重建/删除旧容器。** 先停止写入，检查并导出旧 API/Worker 中这些目录，
与共享卷中已有内容逐份比对后迁移。PDF 不应盲目覆盖；两个不同的 Chroma 目录也不能
直接覆盖合并，必要时保留原副本后重新构建向量索引。确认全部资料入卷后再更新部署。
本次没有替你迁移既有服务器文件，备份前检查会拒绝仍使用旧配置的部署。

## 如何使用

以下命令均在项目根目录执行。示例 `/mnt/fundscope-backups` 需要替换为服务器上
实际存在且有写权限的独立备份存储；配置文件只由 Compose 读取，不会打印其中的密钥。

### 1. 生成备份

```bash
python -m scripts.backup_restore backup \
  --compose-file docker-compose.prod.yml \
  --project fundscope-prod \
  --env-file .env.production \
  --destination /mnt/fundscope-backups \
  --stop-writers
```

输出中的 `backup` 就是本次备份目录。中途失败会保留 `.partial-*` 供排查，
不把它当作完整备份。普通异常或 Ctrl-C 会尝试启动原本运行的服务；
主机断电、进程被强杀或 Docker 故障不能保证执行清理，运维需要检查并恢复服务。
业务恢复后使用既有 `/readyz` 检查依赖，不要只检查网页是否能打开。

返回 `complete` 仅表示文件捕获完成。源账本不一致、缺 PDF 等问题会保留在基线，
之后的演练报告不会因此给出通过结论。不要只保留文件名就删除上一份已验证备份。

### 2. 校验文件是否损坏

```bash
python -m scripts.backup_restore verify /mnt/fundscope-backups/实际备份目录名
```

这一操作不需要数据库、不调用模型，但**不能证明数据库能够恢复**。

### 3. 实际恢复并核对

```bash
python -m scripts.backup_restore restore-drill /mnt/fundscope-backups/实际备份目录名
```

脚本自动创建随机 `fundscope-restore-*` 项目、新数据库卷、资料卷及内部网络，
无对外端口，不含 API、Worker、Redis 或模型密钥。无需指定目标数据库，
也没有“覆盖当前线上库”的参数。

流程采用 `pg_restore --exit-on-error --single-transaction`。恢复后先核对原样数据，
再隔离旧执行状态。结果保存到备份目录的 `drill-*.json`，退出码 `0` 表示所有核对通过，
`1` 表示失败；默认删除本次演练创建的容器和卷，保留报告和备份。

排查失败时加 `--keep` 保留**隔离副本**。没有主机数据库端口；可用相同
`docker-compose.recovery.yml` 和报告中的随机项目名进入容器检查。
Compose 解析时需要设置临时 `RECOVERY_DB_PASSWORD`，不能把线上密码复制过去；
容器内 `psql` 使用初始化时的环境。检查完只清理该随机项目，不对线上项目运行 `down -v`。

## 报告怎么看

| 字段 | 意义 |
| --- | --- |
| `passed` | 数据、账务、估值完整性、文件、隔离后账本检查全部通过 |
| `checks.business_rows_and_sequences` | 业务表内容、行数和序列与备份时一致，包括账务和 Checkpoint |
| `checks.authorization_rows_and_sequences` | 授权库的表内容和序列一致 |
| `checks.ledger_replay_consistent` | 从有效交易重放的份额、成本与实际持仓投影一致 |
| `checks.valuation_complete` | 持有资产有备份内净值可供计算，不代表净值一定新鲜 |
| `checks.restored_documents` | 真正解压后的文件与清单一致，不只比较输入压缩包 |
| `checks.data_root_permissions` | 恢复资料卷的根目录属主和权限与源卷一致，保留非 root 服务的写入条件 |
| `checks.report_originals_present` / `report_originals_match_database` | 季报 PDF 齐全且内容哈希与数据库一致 |
| `checks.quarantine_keeps_ledger` | 隔离任务没有改动账务结果 |
| `audit.unfinished_jobs` | 恢复前哪些任务尚未结束，供人工查外部执行结果 |
| `audit.usage_needs_review_count` | 预留、执行中或未知用量记录数，不能当作零费用释放 |
| `failed_stage` / `error_type` | 出错步骤与异常类型，不暴露凭据或模型正文 |
| `recovery_point_utc` | 停止应用写入后的备份时点，UTC，不是“任意时间点可恢复” |
| `restore_and_verify_seconds` | 本次隔离启动、恢复、核对与隔离的实测耗时，不包括重新上线业务 |

账务结果使用脱敏的账户/组合标识，逐基金显示份额、成本、待卖出占用、已实现/浮动/合计盈亏。
有更正的原流水不再参与有效计算；部分卖出、全部清仓仍保留已实现盈亏。
同样会检查孤儿记录、断裂/循环更正链、确认订单缺流水、卖出占用超额。
旧的纯权重模拟组合没有真实流水，标为 `allocation_not_applicable`，不伪称交易对账通过。

这是**系统内部一致性核对**，不是与银行、支付宝的外部对账，也不是审计认证。
业务和核对复用同一成本函数，避免两套规则漂移；这能发现数据不一致，但不能单独证明
成本规则本身不存在缺陷，因此仍保留已知结果的单元测试。

## 为什么恢复后不直接启动任务

备份中显示“执行中”，不代表那次请求没有在模型供应商或其他外部系统完成。
照旧启动 Worker 可能重复调用、重复扣费。当前在恢复副本中：

- 未完成 Job 取消、未消费 Outbox 关闭，旧执行版本失效。
- 有效任务授权撤销、旧登录 Session 清除；OpenFGA 关系仍保留作为恢复核对资料。
- 每日简报和监测策略关闭，Cron 文件移到 `recovery-disabled-schedules`。
- API 与 Celery 启动会检查 `RECOVERY_HOLD.json`，存在就拒绝启动。
- 不改基金交易和费用账本，不自动撤销待处理基金订单，不把未知模型用量改成免费。

真正灾难恢复上线还需运维审批：保存原始演练报告，人工核对未完成任务的外部结果及费用，
处理待确认交易，使用新 Redis、重新登录/授权，只重新提交确认需要重做的任务。
检查数据路径、密钥、迁移版本与 `/readyz` 后，才由运维解除启动标记并逐步启用业务。
本版提供验证与隔离工具，**不自动切换生产流量、不自动批准恢复上线**。

## 验证方式

不访问 Docker 的单元测试：

```bash
python -m unittest tests.test_backup_restore tests.test_portfolio_trades tests.test_portfolios
```

真实 PostgreSQL 演练，需 Docker 运行：

```bash
RUN_RECOVERY_DOCKER_TEST=1 TRACE_ENABLED=false AGENT_TASK_AUTHORIZATION_ENABLED=false \
  python -m unittest tests.test_backup_restore.DockerRecoveryTests -v
```

测试仅创建随机项目、使用合成持仓、季报字节和授权数据，不连接已有业务库，不调用大模型。
其中 API/Worker 是占位进程，授权库是合成表，Checkpoint 是字节夹具；
这验证 dump/restore、内容一致性、文件恢复及隔离机制，不等于完成了真实 OpenFGA/API 的上线验收。
正式部署仍须用自己的备份进行演练，并单独验证登录、授权、检索和报表读取。

衡量恢复能力时，应报告最后一份已验证备份距故障多久、恢复用了多久、账务核对有无差异。
一次本地小样本耗时不是生产 RTO 承诺；备份频率决定可能丢失的数据窗口。
需要任意时间点恢复时再建设基础备份与连续 WAL 归档，普通 `pg_dump` 不提供 PITR。

参考：[PostgreSQL 16 逻辑备份](https://www.postgresql.org/docs/16/backup-dump.html)、
[pg_restore 参数](https://www.postgresql.org/docs/16/app-pgrestore.html)。
