# 季报问答稳定性优化复盘

## 这轮解决什么

把“请求失败了”变成能定位、能复现、能比较的工程问题。没有新增分析 Agent，
没有更换模型，没有调整金融结论的判定规则，也没有自动刷新外部市场数据。

执行链路仍然是：

```text
当前问题与会话中的两期报告引用
→ 原有 Agent 选择季报工具
→ 混合检索 + 经理章节 + 资产表
→ 整理本轮可见证据，标原句编号
→ 模型生成结构化回答
→ Python 校验
→ 必要时仅修正一次，再校验
→ 保存已核对答案及每轮诊断
```

## 一、补齐逐轮诊断

- `ReportExecution` 升为 `fund-report-runtime-v2`，沿用 JSON 存储，不新增数据库表。
- 每次模型尝试记录输入字符数、消息条数、输出字符数、耗时、结束原因、供应商返回的 Token 用量。
- 字符数统计消息`content`，不包含HTTP包装、工具Schema与独立的工具调用参数；不是完整请求Token数。
- 只记录推理 Token 的数量，不保存模型思考内容、提示词正文或失败草稿。
- `validation_checks` 分开保存 `initial` 和 `final`，包含程序生成的错误、修正状态。
- `report_quality.turns[]` 保存每轮的 `answer_alignment`、`usage`、`execution`；不再只保存末轮详情。
- 如果第二轮超时，`execution_diagnostics.turns[]` 仍保留第一轮已完成的结果。
- 超时请求无法取得完整供应商用量时，`usage_complete=false`；已知用量不等于账单总额。

阶段状态 `ok` 表示该段代码执行完毕，不等于引用通过；引用是否通过看
`validation_checks` 及最终 `answer_alignment.status`。两者避免混淆。

这说明一次重新运行可能改变完成结果，不应把这种波动直接说成优化收益。
原先的三个失败也并非都由检索或账户余额引起。

针对性改动：

1. 同一原文可能以普通检索摘录、经理章节两种身份出现。优先展示经理章节，
   只去掉被同基金、同版本、同页经理片段完整包含的普通摘录。部分重叠和其他页的内容不删除。
2. 保持经理原句字符与编号不变；提示词显式列出本轮可用于经理对比的编号。
3. 提示词改成先选依据、再写判断的紧凑协议，明确关系与推断分类的组合要求。
4. 修正提示中提供同页文字相含的经理句候选，由模型重选；Python不悄悄替换引用。
5. 修正请求只传一份协议和一份草稿，保留历史消息与实际工具对象，避免重复上下文。

上述首轮候选也真实运行了一次：`eval_d71d8a5c14f343c4`，0/3通过。
商业航天两个场景仍超时；债基风险题暴露出`after`引用超过两条，修正时原样重发。
这次失败保留，不能声称仅缩短提示词就已修好。

因此继续作了两项有明确原因的调整：

6. 只问经理文字的场景进入`manager`视图，保留经理原文及相关召回，不传整套未请求的资产表。
   配置数字、持仓、买卖、因果等混合问题仍回到full，数字题仍沿用allocation。
7. Pydantic错误不只显示`too_long`，而是明确“最多2，实际3条引用”，要求按主题拆分，
   不丢掉关键依据；错误消息不包含原始草稿。

该候选完整跑20题：`eval_71fb206664fa43f0`，仍为17/20，849.95秒。
商业航天主题题恢复完成，但多轮首问和债基风险仍整理超时，另有预测题跳过取证而被后端拒绝。
与历史基线相比整组更慢，不能宣称这组修改已经提升通过率或降低延迟。

据此再增加有边界的恢复策略`manager-timeout-fallback-v1`：

8. 仅在已经取得证据的经理文字题，为整理轮预留最后15秒；默认思考调用超时后，
   若仍有尝试次数和至少3秒预算，使用同一模型、同一实际ToolMessage关闭思考整理一次。
   这15秒从已有整理阶段预算中扣出，不与原预算叠加；一般先用约70秒，再保留约15秒兜底，
   具体时间扣除本次准备和检索消耗后计算。成功就立即返回，不固定等满。
9. 总尝试次数仍最多2次。原恢复层已用完次数、用户取消、余额/认证或参数错误时，不追加调用。
   一次引用修正仍另受原有20秒上限与110秒总预算约束；快速整理失败也不能输出未经核对的草稿。
10. 显式记录使用的`strategy`、`synthesis_policy`及思考设置变化，保留失败尝试。
    缺失的超时账单用量仍标记未知，不能拿最后成功调用的Token当成全部成本。
11. 经理问题混入“多少、几只、权重”等数值要求时回到完整视图；季报路由提示明确，
    即便认为历史资料不能回答预测，也应先取证后说明缺口。若模型仍跳过工具，原校验会拒绝无证据结果。

默认仍是 `deepseek-v4-pro`、`standard`、hybrid、`text-embedding-v4`、1024维。
总预算110秒、模型阶段上限90秒、一次修正上限20秒均未增加，考卷和评分规则保持不变。
执行策略不再完全相同：本轮加入了超时才启用的非思考整理。对照报告会注明这一差异，
不能把结果描述成“所有推理参数都不变的实验”，也不把快速兜底泛化到普通Agent或未知问题。

## 四、查看与复现

日常入口不变：在网页或小程序中选择两期季报，进入AI投研提问，再直接继续追问。
新问题会使用当前代码，历史已保存回答不会被自动改写；不需要重新抓季报或重建产品索引。

管理员可通过既有`GET /api/v1/evals/runs/{run_id}`读取完整评测JSON，沿用原登录与用户隔离。
普通用户不能凭一个运行ID读取别人的记录。本机对照脚本不需要在命令中放模型Key。

诊断位置：

- `turn`是用户第几次提问：第一次问机会，第二次追问风险。
- `round_index`是这次提问内部的Agent循环：例如第1轮选择工具，第2轮根据工具结果生成答案。
- `attempt`是同一模型调用第几次尝试：例如第2轮第1次超时，第2次快速整理完成。

因此“第2轮模型超时”不一定是用户第二次提问失败；结合`turn + round_index + attempt`定位。

| 想知道什么 | 字段 |
| --- | --- |
| 哪轮失败、前一轮是否完成 | `results[].report_quality.turns[]`，执行失败时看`execution_diagnostics.turns[]` |
| 准备、检索、生成、校验、修正分别耗时 | 每轮`execution.stages[]` |
| 哪次尝试超时，是否启用快速兜底 | 每轮`execution.model_attempts[]`的`status`、`strategy` |
| 首次检查错误与修正后错误 | 每轮`execution.validation_checks[]`的`initial`与`final` |
| 修正是否实际解决问题 | `repair_status`：`not_needed/corrected/rejected/failed` |
| 本轮原文、页码与解读 | 每轮`answer_alignment.statements[]`，正文仍由后端生成 |
| 是否获得完整调用用量 | 每轮`execution.usage_complete`；只讨论已知用量时看`usage` |

阶段`status=ok`但最终`answer_status=limited`，表示执行完成但回答不合格；不是接口成功就算分析成功。

代码阅读顺序：`fund_report_runtime.py` → `recovery.py` → `tool_agent.py` →
`fund_report_query.py` / `fund_report_sentences.py` → `fund_report_answer.py` →
`fund_report_evals.py` / `fund_report_eval_comparison.py`。

## 验证边界

离线测试验证引用隔离、同页去重、压缩后引用范围、单次修正、取消/超时传播、
首轮结果保留以及对照条件检查。真实模型测评另行记录，不把假模型的测试结果当成真实能力。

最终相关后端测试248项通过，前端既有回归177项通过。后端新增覆盖：
兜底前后同一ToolMessage对象和原截止时间、两次都超时仍不追加第三次、剩余尝试耗尽即止、
取消与不可恢复错误传播、已知/未知用量分开，以及执行策略差异在对照中明确提示。
这是相关测试集合，不是声称整个仓库全部测试已运行；未新增微信真机验收。

自动通过率不是语义准确率。选中了合法原文，也仍需检查解读是否受原文支持、是否漏主题、
是否混淆回顾与展望。固定20题的小样本耗时不是生产SLA，也不代表高并发性能。
